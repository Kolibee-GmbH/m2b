# Behavior: the curation run

The rules about the curation run: when it is due and how it starts, what its steps do with the
inbox, the sessions, the task list and `memory/`, the fence around a model step and the check of
what a step did to `memory/`, the proposals and their answers, the review task and the commit of a
run.

It is one of the four parts of the [behavior catalog](../behavior.md), which says what stands where.

## Behaviors m2b keeps

| ID | Behavior | Why |
|---|---|---|
| B11 | The curation nudge only starts the runner detached and returns at once | the session must not wait for curation |
| B12 | A run is due 20 hours after the last successful run or when the inbox holds a visible file (hidden files do not count), unless the backoff after a failed run (1, 4, 20 hours) has not passed | runs when there is work |
| B13 | A failed core step keeps the run due; the last successful run moves only after a run whose core steps all succeeded. A failed add-on step, a failed reading of the sessions (B119), a task for the waiting proposals that could not be brought up to date (B124), or a commit of the run that failed (B141), is reported in the review and leaves the run succeeded | a partial run must be repeated, but an add-on that keeps failing must not hold back the filing of the inbox |
| B14 | Findings that need the owner and failures of a run go into the one review task, with the time of the run; a clean run completes it | one place to look |
| B15 | There is only one review task; it is found by its marker, open or completed, and reopened, not duplicated | a review found by title became two when renamed |
| B16 | Ingest is restart-safe: tasks are created before the move, recorded in frontmatter, and the move into the archive is the last step; a rerun never creates a second task or a second archive file | a crash at any point loses nothing |
| B17 | Ingest never adopts a task by its title; it finds its own tasks by the capture marker in their notes | recurring tasks share titles; adopting by title could swallow a real one |
| B18 | A missing `created` is filled from the file's modification time with offset; a missing `source` from a conforming name, else `cli` | files dropped into the inbox by hand |
| B19 | The month folder follows `created` in UTC, for text and binaries alike | one time base (X5) |
| B20 | A binary bundle gets its sidecar at normalize time (the only moment the original name is known), a reading copy where needed, and the sidecar moves last; a rerun on any member completes the rest | a bundle is never half in the archive |
| B21 | Lint reports schema violations, evicted files, broken links, facts missing from the index, an oversized distillate, orphaned sidecar references, binary volume. `lint fix` removes only verified conflict copies, in the archive and of task files (B157), and our own leftover temp files; the lint skill may repair a broken link in `memory/` when exactly one archive file matches | reporting is safe, deleting is not |
| B22 | `[[links]]` point to archive files only, always with extension | links without extension once broke silently |
| B23 | The journal appends completed tasks per month, deduplicated by (task id, completion date), existing bytes kept, curator tasks left out, nothing before `journal_since` | an append-only record of what got done |
| B34 | Harvest writes the capture before deleting the candidate task and recognizes its own earlier captures by `from_candidate` | a crash between the two steps neither loses nor doubles a fact |
| B35 | A candidate equal to an open one or to one dropped within 90 days is refused | the same proposal must not come back daily |
| B36 | A fact file never links the same capture twice, and `facts_filed: true` stops a rerun from filing the capture's facts again | a crash between filing facts and the move must not double them |
| B40 | A fact that stops being true on a known day carries `until: YYYY-MM-DD` in its fact file, a current item ends in `(since YYYY-MM-DD)`, both set when the line is written; lint reports one that is no date | a dated line would otherwise stay in every session after its day, as long as no capture touches it; only the writer knows the date for sure |
| B41 | A curation run finds the facts past their `until` and the current items whose `since` lies more than 30 days back in code; it starts the model only for due facts, allowed to edit the distillate and those fact files alone, and rewrites each so it is true today | a dated fact must not mislead every session after its day, and checking every line at every run would cost a model run for nothing |
| B42 | A current item whose `since` lies more than 30 days back becomes one task "Still current? ..." (never two for the same item); at the next run, ticked keeps it with `since` set to that day, dropped or deleted takes it out of Current, and the task goes after the distillate was written; a question whose item changed meanwhile is closed | whether something is still going on only the owner knows, and a question that is applied twice after a crash must change nothing |
| B43 | `m2b curate --refresh-all` runs once, due or not, and its refresh step also gets the fact files without `until` and the current items without `since`, allowed to edit the distillate, the due fact files and the fact files of its batch, and read `corpus/`; it dates a line only where the evidence names the day, and every other run never sees the undated lines | lines written before dates existed would otherwise never expire, and guessing a date for a lasting fact would make it expire wrongly |
| B48 | Lint reports a `###` heading in the facts or the current section that is no topic, and a topic in either with fewer than two or more than five words, a word under three or over 40 characters, a name over 60; the size target counts per view, a topic's current items with its facts | a broken heading decides wrongly when facts come in |
| B51 | `m2b curate --sort-facts` runs once, due or not, with a fenced step that may read `memory/` and edit only `MEMORY.md`; afterwards code compares: when a facts line, a line outside `## Facts` or any other text changed, the old file goes back and the step fails | the model may only move lines and write topic headings, and an edit could change a statement without the fence noticing |
| B53 | Outside a curation run, the commands that move, rename or edit store files (`ingest normalize`, `task`, `ref`, `note`, `facts-filed`, `finish`, `harvest`, `journal`, `lint fix`) exit 2 with one line naming `m2b curate` and change nothing; `m2b --help` does not list `ingest`, `harvest`, `journal` or `hook` | clients only add; a session or a skill that calls a curator step by mistake must not file half a capture |
| B54 | Before the refresh model step code takes a snapshot of `memory/`; afterwards only the due fact files and the distillate's lines for them may differ (in the backfill also the current items it was given, by their `(since ...)` alone); any other change, also after a failed step, puts `memory/` back and fails the step | refresh may change exactly what is due, and its model reads archived text the code does not control |
| B55 | Ingest and lint model steps keep their edits, and code lists every facts line they removed or rewrote and every fact file they emptied or removed in the review task, with the captures filed in that step and where `memory/` as it was before the run is kept (machine state, one copy per run); these findings come back in every review until the owner completes the review task, and a copy goes only when no waiting finding names it | their edits are many and legitimate, but a capture asking to clear the facts must not silently empty every later session, and the next run must not bury the finding |
| B56 | A line a model step writes into `memory/` that holds bidirectional controls, zero-width space, word joiner, invisible operators, a byte order mark or tag characters puts `memory/` back as before the step and fails it (the sorting step's file likewise), and takes `facts_filed` off the captures still in the inbox that gained it in the step; what text people write carries undoes nothing: the joiners, the direction marks, the selector after an emoji, a soft hyphen (the hooks take these out before a session reads the line, B143) | such a line reads one way to the owner and another to the model, and the distillate enters every session |
| B57 | An inbox file ingest cannot file (a name or date normalize cannot handle, a text that is not UTF-8, a schema-named capture in a subfolder) is noted with its modification time after an ingest step that ran to its end and saw it; while it is unchanged it makes no run due and starts no ingest model step, and every run names it in the review | one export the codec cannot read would otherwise start a model run at every session start, for ever |
| B58 | The questions "Still current?" are kept with the task list they were asked in; a question missing from another list is asked again there, not counted as deleted | after setup switched lists the owner never saw the question, so no item may leave Current for it |
| B61 | Every model step runs fenced: `claude -p` from an empty folder, `--setting-sources project`, `--permission-mode dontAsk`, and either this plugin alone with only the commands and store paths of its step, where a denied call fails the step and becomes a finding, or, for a step that only reads a text and answers, no plugin, no tool (`--tools ""`), no MCP server, no skill, one turn and no session kept on disk, the text on standard input | a model that reads captures must not reach the owner's settings, other plugins or anything outside its step; a model that reads what a person typed has nothing to call at all, and the text is not written a second time under Claude Code's folder |
| B62 | Only the machine `store.json` names curates; any other refuses into its local log and exits 0 | iCloud gives no lock shared between machines, so two curators would file the same inbox twice |
| B63 | One run per machine, held by a lock that every child of the run keeps; after a failed run the next attempt waits 1, then 4, then 20 hours, even over a full inbox; a run in which only steps failed that leave it succeeded (B13) starts no wait | a failure that does not clear by itself must cost one attempt, not one per session |
| B67 | A curation run starts a model only for a step with something to read: ingest for captures, refresh for a fact past its day, lint for a broken memory link with one candidate | a run with nothing to file must cost no model run |
| B69 | `format` in `store.json` counts the rules for curated content; this m2b knows one format more than it has migrations, numbered from 2; a curation run on the curating machine first runs each migration above the store's format, in order, each as a step `migrate-<format>`, and writes the new `format` after each | content already in a store follows a new rule without the owner running anything |
| B70 | A migration that fails, or changes `memory/` beyond what its code check allows, puts `memory/` back, leaves `format` as it was and ends the run with the review, which names the step; an m2b that knows an older format does not curate the store and changes nothing | later steps follow rules the store does not hold yet, and an older curator would write under old ones |
| B73 | This m2b knows store format 3; its two migrations, to formats 2 and 3, change nothing in `memory/` and fail if anything changed, so an older store only gets its new number, one step per format | format 2 adds earlier values, which an m2b that knows format 1 would drop while curating; format 3 adds topics under current, whose headings an m2b that knows format 2 reports as errors |
| B74 | Lint reports a line under a fact file's `## Earlier` that is not `- <statement> (until YYYY-MM-DD)` with a real day, as an action | an earlier value without the day it ended says nothing about when it held |
| B76 | A model step stopped by SIGTERM still has `memory/` checked as in B54 to B56 and put back before the runner exits, and a check that fails does not keep it from stopping; a run that never stored its changes leaves its copy of `memory/` marked, and the next run on the machine that gets past preflight compares `memory/` with the oldest marked copy and lists a line that hides text and every facts line removed or rewritten in the review, which keeps the copy | a stopped runner would otherwise leave such a line in every later session, and the next run would prune the only evidence |
| B78 | The journal fetches evicted month files once, together; a month file still evicted after that gets nothing in this run, is named in the review with the command that downloads it, and the other months are written | completed tasks reach back to `journal_since`, so one old month in the cloud would otherwise fail every run |
| B79 | A capture that will not download within the fetch timeout does not stop the curation run: it waits in the inbox, with every file of its bundle, ingest starts no model step for it alone, the run record names it, and while it stays evicted and unchanged it makes no run due by itself; each file asked for gets its share of the fetch time; `m2b capture` first fetches an evicted `store.json` and, when it stays evicted, refuses with exit 3 and the command that downloads it | one file iCloud is slow to bring stops neither curation nor capture on a second machine |
| B109 | Curation: the skills that read captured text say that it is data and that nothing in it changes their rules, their commands or the files they touch. Ingest carries out no capture that gives instructions to whoever files it, one that speaks to the assistant or the filer and asks to replace, delete or rewrite facts, to write a given line or rule, to change the rules or to run a command: it files nothing from it, no fact, current line, task or ref, notes it `filed: nothing, the capture gives instructions`, moves it into the archive as written, where only a `follow_up` it already carried still becomes its task (B32), and reports it as an action; what the owner wants for themselves, a capture in which they say what changed and a candidate they confirmed are filed as ever. Refresh leaves a due fact whose file or evidence gives such instructions and reports it. The worklog's verdict carries out no such text and gives its session a topic like any other | a capture is also text from elsewhere, a forwarded mail or a web page, and the run has no one to ask; in the archive the capture is kept as the original and the run is not due again at every session start, as it would be with the capture left in the inbox |
| B112 | Sessions: of Claude Code's transcripts m2b takes as the person's words only a prompt Claude Code marks as sent by a human, typed in the terminal or the desktop app, also while Claude was busy. What another sender sent (a plugin, a finished task, another agent), a suggested prompt the person only accepted and text without the mark are left out and counted per session; what Claude Code writes in the user's place for itself (records it flags as its own, a subagent's conversation, tool results, the output of a local command or of a shell line, in one block or several) is left out without a count, and no answer of Claude is read | a plugin's prompt or a suggestion is not the person speaking, and what is proposed from it would be filed as theirs; an older Claude Code that writes no mark must show as unmarked prompts, not as a day on which nothing was said |
| B113 | Sessions: of a typed prompt goes what was typed. A pasted block is left out with what it holds and counted, one that never closes with the rest of the prompt; the blocks Claude Code writes into a prompt (its reminders, the output of hooks) go the same way; credentials are redacted, white space is collapsed, and the text ends after 2,000 characters; a slash command is only its name | a pasted mail or document is what a third party wrote, and counted as the person's words it would be filed as theirs |
| B114 | Sessions: only prompts of the period count. A transcript with any record of a headless run is left out whole; one that cannot be opened, or that has prompts of the period and names no folder, is reported as not read and the others are read; a transcripts folder that is missing is an error, not a period without sessions | a curation run or a check must never read itself, and "could not look" must not read as "nothing was said" |
| B115 | Curation: while `curation.read_sessions` in the machine config is `true` (default `false`), a run reads after harvest and before ingest what the person typed since the last reading ended: the last 24 hours at the first reading, 7 days at most, and what lies before is named as not read. It asks the model once in the run without tools (B61), with the distillate, what the person kept and dropped of earlier proposals (B134) and per session its folder, its day and its prompts, keeps the proposals that pass the checks (B117) in `state/core/proposals.json` (B118) and reports its counts as information, never in the review, with what the reader left out of the sessions it read (B112, B113). With no session that has a typed prompt no model starts. While the switch is off the step is not in the run | the transcripts hold every project's sessions on this machine, so reading them is the person's decision; a model run for a day on which nothing was typed costs for nothing |
| B116 | Curation: a session that started in or below a folder the profile's `worklog_leave_out.path_under` names, compared as written, or one of `distillate.skip_under` in the machine config, does not reach the model and is counted, and so does a session whose folder is not an absolute path, which cannot be compared with either; when no other session is left, no model starts | work under a confidentiality agreement must not reach a model through a second door; one list of folders m2b never reads cannot be forgotten in one of two places |
| B117 | Curation: a proposal is kept only when its quote stands, white space aside, with at least three words in one prompt of the session it names. It is not kept when the person captured it themselves in the period: the quote stands in a capture, a capture of at least three words stands in the quote, or every word of a capture stands in the quote's prompt and capture and quote share four fifths of the shorter one's words; a text file dropped into the inbox under a name of its own counts as a capture of the period. An entry of the answer that is not in the form (a kind that is none of the four, a text over 300 characters, a topic over the 60 characters a topic's name may have, a session that was not given, a day that is none, characters that hide text) is left out. Each of the three is counted; an answer without a list of proposals is an error, not an answer without proposals | "never a guess" as an instruction is a hope, as a check it is a rule: what the person sees next to a proposal are their own words; what they captured themselves must not come back as a proposal |
| B118 | Curation: a proposal's id comes from its session and its quote alone, white space aside. A proposal whose id or whose text, case and spacing aside, is that of an open proposal or of one kept, dropped or expired (B131) within 90 days is refused and counted, also within one answer; so reading a period a second time adds nothing | a reading that failed after the model answered is repeated by the next run, and the same fact said in two sessions is one proposal; what the person dropped must not come back with the next reading, and what they kept is filed in the proposal's words, not theirs, so only the proposals file knows it then |
| B119 | Curation: when the reading of the sessions fails (the transcripts cannot be looked at, nothing in the period carries Claude Code's mark of who sent it while texts without it are there, the model gives no answer, its answer cannot be read, the proposals file cannot be used), the review says so and that the next run reads them again, the run counts as succeeded and starts no wait (B13, B63), ingest and the later steps run, nothing is saved and the time up to which the sessions are read stays | the step reads a file format Claude Code does not promise; its failure must not hold back the filing of the inbox, and a period it could not read must not be lost |
| B120 | Proposals: keep and drop are answers a client adds, one empty file each, created exclusively: `state/core/proposal-answers/<id>.keep` or `<id>.drop`; an answer never changes the proposals file. A proposal that has an answer, as a file or settled by a run, gets no second one, and the client hears which answer stands; one unknown id and no answer is written. The answer is the file's name: a file that is not downloaded counts, an answers folder that is not downloaded is could not look; where a keep and a drop for one proposal meet, keep stands | clients only add to the store, and the band on a second machine must be able to answer; a fact kept by mistake can be removed, one dropped by mistake is gone |
| B121 | Harvest settles the answers to proposals in every curation run, whether or not it reads the sessions and also when the task list is out of reach: for a kept proposal it writes the capture first (source `proposal`, `from_proposal`, the proposal's text; a commitment that names its day gets its follow-up task with it, B32), then marks the proposal kept in the proposals file, then removes the answer file, and it recognizes its own earlier capture by `from_proposal`; a dropped proposal is marked dropped. Both stay known for 90 days (B118). An answer to a proposal that is kept, dropped or not known only loses its file, and so does a drop of an expired one (B131). With a proposal capture that is not downloaded or cannot be read no kept proposal is captured; answers or a proposals file that cannot be read leave the answers waiting; the review says which, also when the harvest fails over the task list | nothing is filed before the person said keep, and a crash between two steps neither loses nor doubles a fact |
| B122 | `m2b proposals` lists the open proposals without an answer, the earliest said first, each with its id, kind, text, the person's words and the day they were said, and says how many answers wait for the next curation run; white space in a text is shown as single spaces and any other control character is written out, never sent to the terminal; `--json` gives the same. `keep <id>...`, `keep --all` and `drop <id>...` add the answers (B120): the same answer a second time is said, another answer than the one that stands ends with exit 1 and changes nothing, an unknown id is an error before anything is written. A proposals file or an answers folder that is not downloaded is could not look, with the command that fetches it (B6) | the person answers the proposals together, also without the band; "could not look" must not read as "nothing waits", and what the person keeps is what the listing showed them |
| B124 | Proposals: while proposals wait for an answer (B122), the task list holds one task for them, never one per proposal, found by its marker `m2b:proposals`, open or completed, whatever its title; its notes say in the profile's language how many wait and where they are answered. Every curation run brings it up to date as its last step before the review, whether or not it reads the sessions: the number follows what waits, and once nothing waits the task is completed. When what waits cannot be looked at, or the task list does not answer, the task stays as it is, the failure is in the review and the run still counts as succeeded | the task list is what a phone shows, and one reminder per proposal is what a cap on proposals would have been needed for |
| B125 | Proposals: the task for the waiting proposals is a sign and no answer: completing, dropping or deleting it keeps and drops nothing, and it is neither one of the person's todos nor journaled as their work. A task put away comes back, reopened or made anew, only when a proposal was added after the newest one an open task told of (`announced_until` in `proposals.json`), and then says how many wait in all; an answer alone does not bring it back, and a task that could not be written is made by the next run | a task that came back with every run could not be put away, and one that never came back would hide what was proposed since |
| B131 | Proposals: an open proposal that has no answer 14 days after it was added expires: it waits no longer (B122, B124, B126), stays known for 90 days so that it is not proposed again (B118), and is counted (B132). One whose answer waits for a run does not expire, however old it is, and when the answers cannot be looked at none expires. A keep by its id is still taken while it is known, and harvest files it like any keep (B121); a drop of it only loses its file. Every curation run does this in its last step before the review, whether or not it reads the sessions: it names in the run record how many expired, and removes the proposals kept, dropped or expired 90 days ago or longer | a list that only grows is one nobody opens, and no answer is not a drop: it says the person did not look; a keep that reached the store late, from a machine that had not seen the proposal expire, must not be lost; what a run forgets must not depend on whether that run asked a model |
| B132 | Proposals: the proposals file counts per kind (`counts`) how many proposals were added (`proposed`) and how many of them ended kept, dropped or expired, each under how it ended, so one kept after it expired counts as kept; and how many more the quote check refused (`not_quoted`, B117), which were never added. A count stays when its proposal is removed; one that is no number, or of a kind m2b does not know, reads as nothing counted | whether a kind is worth proposing to this person shows only over more proposals than the file remembers |
| B133 | `m2b status` shows what share the person kept of the proposals they answered in the last 30 days, by the moment a run settled the answer (`proposals: kept 2 of 3 answered in the last 30 days (67%)`), and how many expired without an answer in that time; `--json` gives the numbers, the share (`keep_rate`) and the counts per kind (B132) under `proposal_answers`. Expired proposals are not part of the share, and without an answer in the 30 days there is none (`null`, `no answer in the last 30 days`), never 0%. On a machine that does not read the sessions, in a store that holds no proposal and no count, the part is absent; a proposals file that cannot be used is could not look, with the reason | the share tells the person whether the reading proposes what they want; an expired proposal says they did not look, not that it was wrong, and "none kept" must not be read from "none answered" |
| B134 | Curation: the reading of the sessions (B115) shows the model, under `answered` in its input, the proposals the person kept and those they dropped, of each the 30 a run settled last within 90 days (B118), the newest first, each with its kind, its text and the person's words. A proposal that waits or expired (B131) is not shown, and before any answer both lists are there and empty. The run says in its information how many it showed. The instruction tells the model to leave out what is like a dropped one and never to propose an example; a proposal that quotes an example and no prompt of the period is refused by the quote check like any other (B117) | what this person keeps and drops says more about what to propose to them than a rule written for everybody; no answer says nothing about a proposal, so an expired one teaches nothing; an example is what the person typed in another period, and a proposal standing on it would bring back what they answered already |
| B152 | Curation: a session does not reach the model when a part the profile's `worklog_leave_out.git_remote_contains` names is in the URL of a remote known for the folder it started in: one noted there at a session start (B151) or one git names there at the run. A part is compared without regard to case, an SSH address `git@host:owner/repo` or `git@host:/path` also as `host/owner/repo` and `host/path`, a URL also without its port. A session for whose folder nothing is noted and git says nothing (the folder is gone, the machine has no git to start, git fails or does not answer) does not reach the model either while the profile names a remote. Both are counted in the run's information, each under its reason. While the profile names no remote, git is not asked and no session is left out for its repository | a list of folders misses the checkout nobody thought of, where a remote names the repository once; a session whose repository cannot be told may be the confidential one, and a model that has read it cannot unread it |
| B137 | When a dropped or deleted "Still current?" question (B42) takes a topic's last item out of the current section, the topic's heading there goes with it when only blank lines are left below it; the topic's heading in the facts section, a heading that is no topic and a topic that keeps an item stay, and a ticked question dates the item where it stands | every session start names every topic, so a heading without an item would keep naming one that holds nothing |
| B138 | Curation: the ingest skill puts a current item by the question it asks for a fact. What any session needs goes above the first topic of the current section; what concerns one subject (work for a customer, a project of an organisation, a club) goes under that subject's heading there, which is the topic's heading from the facts section, copied, or for a subject without a topic a new one by the rules for topics (B48). A line above the topics that is about one subject only moves under its topic when a capture of the run is about the same thing; a line under a topic stays there, and a line no capture of the run is about stays where it is; a heading whose last item goes, goes with it there; the day's worklog note is filed by the same rule. The distillate the skill shows has a current item under the topic of its facts. The sorting step (B51) gives a topic that stands under current the heading it has there | every line above the topics reaches every session (B136), so the work for one customer would be named in a session about another; the run has no one to ask where a line belongs, and a model writes what its example shows |
| B139 | Curation: when the store folder is the top of a git work tree and git is on the machine, a run ends with one commit of what changed in the store while it ran: every visible file written, moved or removed in those minutes, the finished run record and the task files among them. What else lies uncommitted or staged in the work tree stays out and stays as it is, and so do hidden files and files git ignores. A run that changed nothing but its own record makes no commit, and neither does a run stopped at preflight or before its end. Without a `.git` in the store folder, without git on the machine (on macOS: without the developer tools, whose stand-in for git is never started), or with `curation.git_commit` set to `false` in the machine config, nothing is done and nothing is reported | a curator that rewrites memory by itself needs a net the owner can pull: `git revert` takes one run back, and whoever keeps no repository must not notice any of it |
| B140 | The commit of a run (B139) is m2b's own and touches nothing else of the repository: author and committer are `m2b <m2b@localhost>`, the message names the run's start and how its steps ended; m2b creates no repository, writes no git configuration, never pushes, runs no hook and signs nothing, and of the index it brings only the committed paths up to date. It commits onto HEAD as it is: a HEAD that moved while it worked, or a merge, rebase, cherry-pick, revert or bisect the owner has not finished, means no commit | the repository is the owner's; a run in the background has nobody to answer a prompt, and its commits must be told apart from the owner's own work |
| B141 | A commit of a run (B139) that fails leaves the run as it ended: the failure is the failed step `commit` in the review task and the run record, and no wait starts for it (B13). git is handed only files that are downloaded (B6): a changed file that is evicted is left out, an evicted `.gitignore` or `.gitattributes` on the way to a changed file stops the commit and names the command that fetches it, and so does an evicted `.git` | the commit is the net, not the work: it must never cost a run, and never be the reason a file is downloaded |
| B144 | Why a model step failed over what it did to `memory/` (B54, B56, B76) is said without any text of `memory/`: a line with a character that hides or reorders text by its file, its line number and the characters' code points; a line the refresh step may not touch as removed, changed or added by its line number in the distillate as it was before the step, which is how the file is again.
