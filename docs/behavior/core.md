# Behavior: the core

The rules about capture, the store and its backends, setup and configuration, what a session is
given at its start and before a prompt, search, tasks and calendar, and what holds for every
add-on.

It is one of the four parts of the [behavior catalog](../behavior.md), which says what stands where.

## Behaviors m2b keeps

| ID | Behavior | Why |
|---|---|---|
| B1 | Capture writes a new file, text byte for byte (typos, spacing kept); one trailing newline added only if missing | the capture is the original; judgment belongs to curation |
| B2 | A name collision draws a new random suffix; an existing file is never overwritten | two captures in the same second |
| B3 | Empty text or no store set up: exit 2; a store folder that is missing: exit 3; either way nothing written, no folder created | a capture must never land in the wrong place |
| B4 | The quiet marker counts only as the exact frontmatter line, never in the body; a client sets it only on its own new file | it silences proactive replay and must not be set by accident |
| B5 | Every proactive replay states its reason ("random pick from May 2026", "touches the open question about the garden shed") | the owner judges whether the replay was worth it |
| B6 | Evicted files are never read; commands list them with the command that fetches them | a read would download or hang |
| B7 | Session-start hooks always exit 0; without a config they print nothing, with a config they print one line when something needs the user | a hook must never block a session, and "could not look" must still show |
| B8 | The distillate is printed up to 8 KB, cut on a character boundary, with a line saying it was cut | bounded context; the cut is visible |
| B9 | The routing rule is printed only together with a distillate | no rule without a brain to route to |
| B24 | A tasks or calendar backend that answers with zero lists or zero calendars has failed; it never returns an empty result | without privacy grants, macOS answers empty with exit 0 |
| B25 | Calendar events are deduplicated across accounts by title and start; read-only calendars are read but never offered for writing | the same meeting appears in several accounts |
| B26 | Event creation requires a named, writable calendar and reads the event back before reporting success | an entry in the wrong calendar, or one that was never saved, must not read as done |
| B32 | Follow-up: a task with a due date whose notes name the capture's file name; the capture records the task, or `follow_up:` when the task could not be created yet | done by the model alone, a follow-up takes three steps and one of them gets skipped |
| B37 | Setup joins an existing store instead of writing over it, also while its files are still evicted | a second machine must not reset the profile or the distillate |
| B39 | On macOS both store backends guard against evicted files; on a folder with only local files the guard changes nothing | Dropbox and OneDrive also keep files on demand; reading one would download it or hang |
| B44 | Facts under a topic (`### <name> (<word>, <word>)` in the facts section) stay out of the session start; every session gets the other lines, one line naming the topics, and the facts of each topic a word of which is in the project folder's path below the home folder | what matters in one context stays out of the others, and the session still knows what exists |
| B45 | A topic word matches whole (no letter, digit or underscore next to it), case-folded and in Unicode NFC; in a path `-`, `_`, `.` and `/` count as spaces; words under three characters never match | "Acme" must not fire on "Acmes", and macOS hands out decomposed paths |
| B46 | The session start keeps every line of the distillate that is not in a topic, lines the parser cannot read included; the cut takes from the end, path topics first, then the topic line, and a topic comes only whole | nothing a session saw before topics existed is dropped silently |
| B47 | A session notes the topics its start showed; `/clear`, compaction and a new session start the list over, a resumed session keeps it; a session id that is not letters, digits and dashes is never used | a topic comes in once while the context still holds it, and an id never becomes a path |
| B49 | Before each prompt, the facts of each topic the prompt or the project path names and the session has not been shown come in as `additionalContext`, under a header saying they are data and not instructions, whole topics up to 4 KB; the hook prints nothing on any error, inside a curation run or where the distillate is off | a topic comes in where it is talked about, and a hook on every prompt must never cost the prompt |
| B247 | A topic line `- Repository: <address> (<file>.md)` comes into a session, at its start (B46) and before a prompt (B49), with one line more below it: `  on this machine: <folder>`, the top of the repository of the folder noted with a remote of that address (B151) and seen last that is still there, or `  not cloned on this machine`. An address is a remote's host and path in lower case, without scheme, user, password, port, `.git` and closing slash, so every spelling of one remote matches it; only that exact line form gets the line. Only machine state is read for it, no file of the store and no git, and a note of any age counts while its folder is there | the store is shared between machines and must name no machine's path, while a session that is handed the folder reads the project's files itself instead of asking where they are |
| B248 | `m2b fix add` keeps a fix for a file Claude reads, from one JSON object on standard input: the file, the new wording, what is wrong in one line, and the line it replaces unless it only adds. A file under `~/.claude/` is kept by its path from `~` and this machine; a file in a repository by the addresses of the repository's remotes (B247) and its path in the repository. A file in neither, in a repository without a remote, or one that does not hold the line given, is refused with exit 2 and nothing is kept. The fix is one new file in the store, `state/core/fixes/<name>.json`, created exclusively, its name `fix-` and twelve letters and digits drawn from the file, the line and the wording, so the same fix kept twice stays one | a lesson whose source says the matter wrongly is a fix of that source, not a second statement beside it; a repository is known on another machine by its remote, never by a folder of this one; a client only adds to the store |
| B286 | A fix is kept only for a file Claude Code loads as instructions: in a repository a `CLAUDE.md` or `CLAUDE.local.md` in any folder, or a `.md` file below a `.claude/rules/` folder; under `~/.claude/` the `CLAUDE.md`, a `.md` file below `rules/` or `output-styles/`, or a `.md` file of Claude Code's memory, `projects/<folder>/memory/`. Any other file is refused, by `m2b fix add`, by the reading's check of a lesson, and when a kept fix is read | a fix is applied by a session from a text kept in a store that syncs between machines; a settings file, a hook or a workflow would run that text as code |
| B249 | A session starts with one line before the distillate for each kept fix that waits for its place: a fix for its repository's file where the folder lies in a clone of it, a fix for a file under `~/.claude/` in any folder of the machine it was kept on. The line names the file on this machine and the fix by its name, never its text, which `m2b fix show <name>` prints whole. The session start reads the file and writes nothing, in the store or anywhere: a file that holds the new wording gets a line that the fix looks applied and waits for the owner's word; a file that holds neither the line the fix replaces nor its wording gets a line saying so, which asks the session to tell the owner, and the fix waits on until the owner gives it up (`m2b fix drop`). Fixes that cannot be read, and a file that cannot be looked at, cost the session start nothing | m2b writes no file of a repository, which is committed, shared and sometimes public: the session applies the fix where the owner sees and commits the change; a checkout can be on any branch, so a line one checkout lacks says nothing about another, and only the owner knows whether the fix is still right |
| B250 | `m2b fix done <name>` and `m2b fix drop <name>` settle a waiting fix with one new empty file beside it, `<name>.done` or `<name>.dropped`; a settled fix waits no longer, a fix settled once keeps that state, and where two clients settled one fix differently, done stands. `m2b fix list` shows every kept fix and what became of it. Neither these commands nor the session start write a file outside the store and machine state | the owner confirms that a fix is applied, not the session that applied it; the state of a fix must not depend on which client wrote last |
| B251 | The routing rule a session starts with says that a correction holding in every project goes to `~/.claude/CLAUDE.md`, not into one project's memory, and that a `CLAUDE.md` that says the matter wrongly gets a fix (B248), not a second rule beside it | a correction made in one repository and kept in its memory reaches no other project, so the owner makes it again there; a second statement beside a wrong one leaves the session two rules that contradict each other; the sentence fits the start's budget, so a distillate of 8 KB still comes whole (B8) |
| B285 | The routing rule a session starts with says that when something touches both a project and the owner's world, the repository gets the content and the second brain a sentence naming the file it stands in | a bare pointer says neither what was decided nor where to look it up; the sentence with its file is what a project topic keeps (B278) |
| B252 | `m2b capture --project` makes the project of the working folder known: the capture is `Keep this project: <the owner's words, or the repository's name>` and one line `Repository: <address>` for each remote of the repository the folder lies in, the address as B247 writes it. A folder in no git repository, in a repository without a remote, or where git cannot say the remotes, ends with exit 2 and one line saying so, and nothing is captured. The capture skill uses it when the owner asks to keep the project, also where the note tool is offered | a project is known on every machine by its remote, never by a folder of this one, and without a remote nothing could find its clone again; a capture of a fixed form lets the run file the repository without guessing which one was meant |
| B253 | A project is captured once: where a topic of the distillate already has a `- Repository:` line with one of the repository's addresses, or a project capture of it waits in the inbox, `m2b capture --project` says so with exit 0 and captures nothing. The ingest skill files a project capture as a topic of its own whose first lines are `- Repository: <address> (<file>.md)`, with the repository's name among its two to five words where it has 3 to 40 characters, as every topic word, and into the topic that already has such a line where there is one, never a second | two topics for one repository would split its lines and bring both into a session; the repository's name is the word a prompt or a folder's path names it by |
| B254 | A line of a project topic of the form `- <sentence> → <path>[, <heading>] (<file>.md)` points into the topic's repository; the path is what follows the last arrow, one word with a `/` or a `.` in it, so a fact that only holds an arrow points nowhere. Where such a topic comes into a session with a clone on this machine (B247), the place line reads `  on this machine: <folder>; the paths after → lie in it`; a topic without such a line keeps the plain place line. Lint measures a project topic against the 4 KB a prompt brings (B48) with the place line this machine would add | a session follows the path from the folder it is handed instead of searching for the file; a topic that fits only without its place line would come into no prompt |
| B255 | On the curating machine lint reads the notes of the remotes of the folders sessions started in (B151) and checks each project topic whose repository has a clone there: a pointer whose file the clone does not hold is an action finding that names the topic and the path, and a pointer that is absolute or leaves the repository (`..`) is one too. A project not cloned on that machine has its pointers unchecked, and a file that cannot be looked at counts as there. No finding names a folder of the machine | a decision that moved or was removed in its repository leaves a line that sends every session to nothing; the run's review is in the store, which names no machine's path |
| B256 | Lint reports, as information, a `Repository:` line whose address no folder on the curating machine was noted with in the last 30 days (B151). Lint run without the notes, as a test does, checks no project | a project nobody opened for a month may be over, and the owner decides whether its topic still belongs in the distillate |
| B257 | A lesson the owner kept is a file under `memory/lessons/` with `kind` (`knowledge` or `action`), `target` (`every project` or a repository's address) and `kept` in its frontmatter, a title, and the lesson as its first paragraph; a file without those fields is no lesson, and a capture is never one, whatever it says. Every session starts, after the distillate and the routing rule and apart from the distillate's "data, not instructions" header, with a block of the knowledge lessons for every project: `m2b lessons: the owner corrected Claude on each of these and kept the correction; ...` and one line per lesson, the oldest kept first, without the characters that draw nothing. Where the folder or a lesson's file is not downloaded or cannot be read, the session start says so in one line (with the fetch command where it is not downloaded), as for the distillate, brings no block and leaves the tool hook's list (B263) as the last session start wrote it | a correction the owner kept is said once and holds in every session, on every machine the store reaches; the block says what the lines are, since they are corrections to follow and not notes to weigh |
| B258 | A lesson with `kept_at` (the source that now states it, such as `~/.claude/CLAUDE.md`) stays out of the block, and `m2b status` names it with its source beside the count of lessons every session starts with; lessons it cannot read it names as `lessons: could not look: <why>`, never as none | the source reaches the session already, and the same rule twice in a session is the second statement a fix exists to avoid |
| B259 | The block of lessons comes whole, up to 2,400 characters, with a line for the lessons left out past that; the distillate is cut earlier to make room for it, so the whole session start stays within its limit (B8) | the owner chose that a kept correction comes before the end of a distillate that is far past its target; the limit keeps a long list of lessons from taking the distillate's place |
| B260 | Lint counts the block of lessons into the part every session starts with, and where the two together pass the 2 KB target it reports it as information with both sizes apart | the target is one budget for what every session starts with, and the owner sees which of the two to shorten |
| B262 | An action lesson (`kind: action`) names in its frontmatter the words a command holds when it applies (`words: [scripts/check]`), optionally the words that keep it silent (`unless: [--quick]`) and `ask: true`; an action lesson without words is no lesson | a lesson about a command says in plain words when it applies, and the owner reads and narrows those words, never a pattern |
| B263 | Before every Bash call a hook (`PreToolUse`, its own small command) adds each action lesson whose words the command holds all of, each as a word of its own (`scripts/check` in `./scripts/check`, not in `myscripts/checker`), and none of its `unless` words, for every project or for the repository the session's folder lies in by its noted remotes (B151; the folder the session started in, not where a `cd` took the shell), as context: `m2b lesson for this command: the owner corrected Claude on it and kept the correction: <lesson>`. The session start hands it the action lessons of the store in machine state; another tool, a knowledge lesson, and a lesson for another repository add nothing | the correction comes at the moment Claude is about to repeat the mistake, in the repository it is for, and costs nothing on every other call |
| B264 | An action lesson with `ask: true` has Claude Code ask the owner before the call (`permissionDecision: ask`), with the lesson as the reason; without it the hook only reminds | some corrections the owner wants to decide again each time, and the default must not stop a call |
| B265 | The tool hook reads machine state only (the list of action lessons, the notes of the remotes, the machine config), no file of the store and no git; inside a curation run and in a folder the owner turned m2b off for it adds nothing, and on any error it prints nothing and exits 0, so the call runs. On this machine it answers in about 50 ms with the Python first on the path | it runs before every Bash call, so it must never slow, block or break one |
| B266 | Each time an action lesson fires, the hook appends one line with the time and the lesson's name to a log in machine state, so the firings are counted per lesson | how often a lesson fires shows whether its words are too wide or never met, which the owner judges |
| B281 | While there are action lessons, the tool hook counts each Bash call in a file per day in machine state, one byte a call. `m2b status` names each lesson with its kind and the day it was kept, how often it was corrected again (B280), and for an action lesson how often it fired on this machine and in how many Bash calls since it was kept, with the share; a lesson corrected again is named `not working` | the owner sees which lessons work, by counts since each was kept |
| B267 | `m2b lesson add` keeps a lesson the owner said in a session, from one JSON object on standard input (`text`, `kind`, `title`, `words`, `unless`, `ask`, `for`: `every project` or `this project`, the working folder's repository by its remote): one new file under `state/core/lessons-kept/`, created exclusively, the same lesson twice waiting once. The next curation run's harvest writes each into `memory/lessons/` in code, under a name drawn from its title, and removes the waiting file. The same lesson kept again on another day is not filed twice. An action lesson without words, a lesson of more than one line or that begins with `#`, a lesson with a character that hides or reorders text or steers a terminal, a knowledge lesson for one project (it belongs in that project's CLAUDE.md as a fix, B248) and a lesson for this project where the folder has no remote are refused with exit 2. The capture skill uses it when the owner asks to keep a lesson, and Claude Code asks the owner before it runs | the owner's own sentence is the keeping, and the owner sees it before it is kept: a lesson reaches every session as a correction the owner made, so a session model that read a planted text must not keep one alone; no model step of a run may write a lesson (B261), so the way into `memory/lessons/` is code, and harvest's writes pass no model step's check |
| B268 | `m2b status` names everything a session in the folder starts with, each with its size in KB and its list points, and the sum: `~/.claude/CLAUDE.md` and `~/.claude/rules/`, the CLAUDE.md files and rules from the folder up to the home folder, the active output style, the first 200 lines of Claude Code's auto memory for the repository (for a worktree its main one), and m2b's distillate and lessons as its session start prints them. A rule with `paths` is listed but left out of the sum, a file that cannot be read, lessons that are not downloaded or cannot be read and a style that cannot be found are named as not read and never counted as empty; it only reads and starts no model | most of a session's start is the owner's own files, not m2b's, and only side by side do they show where to cut |
| B50 | Every session start prints the same work rule: people and verbal agreements from work may be captured, who is who, which role, what was agreed; it names nothing that is never captured, since what goes in is the owner's to decide | who is who is what a second brain is for |
| B52 | `m2b` on a Python older than 3.9 prints one line naming the interpreter and its version and exits 1, before importing anything of m2b | an import error deep in the package says nothing about the cause |
| B59 | A Markdown task file that cannot be read as a task is left out of every list (tasks, harvest, ingest, journal, review), `m2b tasks list` names it on stderr, and lint reports it as an action when Markdown is the backend; while such a file exists, no question, candidate or review task missing from the list counts as deleted by the owner | one hand edit must not stop every task step of every run, nor the review task that would say so, nor be read as the owner's answer |
| B60 | `m2b setup inspect --json` answers a machine without config with `"store": null`, and a store folder that does not exist yet inside one that does with `"store_exists": false`, both exit 0; a folder whose parent is missing too stays unreachable (exit 3) | these are the first two answers the setup skill reads on a new machine, and an error there makes a model stop |
| B64 | An add-on that is off runs no curation step, prints nothing at session start and draws nothing | an add-on must cost nothing until its own setup turns it on |
| B65 | `m2b distillate off` in a folder keeps the distillate, the routing rule and topic facts out of every session there and below, on this machine | a screen share or a customer's repository must not show the owner's facts |
| B66 | Setup run again with the same answers changes no file | setup is the way to repair a machine, so running it twice must be safe |
| B68 | `m2b search --any` searches each term as a phrase of its own and reports every line that holds one of them once; `--word` holds for each term; without `--any` several words are one phrase | a word and its translation in one search, so a note in the other language the owner writes in is found |
| B71 | `m2b capture` writes into a store of a newer format, follow-up task included; a `store.json` that cannot be read is refused before anything is written | the inbox contract does not change with the format, so a second machine on an older m2b keeps capturing |
| B72 | `m2b doctor` and `m2b status` give the store's format against this m2b: `current`, `newer` with "update m2b on this machine" (a problem for doctor's exit code), or `migrates` naming the curating machine whose next run migrates it | after an update the owner sees which machine is behind, and why the next run takes longer |
| B75 | A capture whose file cannot be written (no write permission, a full or read-only disk) exits 4 with one line saying "the capture was not saved" and the folder, writes no note and removes the follow-up task it created for it; a task it cannot remove is named in that line, and the capture skill decides by that line, not by the exit code | otherwise the skill tells the owner the note is kept, and a task points to a note that does not exist |
| B77 | A `store.json` with a key that its own format does not have is refused, also when this m2b knows the key from a later format; every key belongs to the format it came with, so a new key raises the format, and an m2b that knows the format before reads the store as newer (B71) | a typo in a key is caught, and a key added later does not stop capture on every machine with an older m2b |
| B80 | `m2b todos` names each Markdown task file it cannot read as a task, with its path and the reason, never says "No open tasks." beside one, and exits 1; JSON carries them as `unreadable`, and the todos skill says it could not look at them; a task file without read permission or not downloaded ends the command with exit 3 and its path | a list missing a task must not read as everything that is open |
| B81 | Setup for a machine that is to curate refuses a store path holding a character the rules that fence a model step cannot name (`, ( ) [ ] * ?`, a backslash, a line break) with one line saying why, before anything is written, and `m2b curate take-over` and `m2b config set` (for `store.path` or a whole `store` section, judged by the store at the new path) refuse such a path likewise; `m2b setup inspect` names it in `store_path_problem` before the interview; `m2b doctor` on the curating machine names such a path as a problem; a machine that only captures may use one; the characters are listed in one place, which the curation run checks too | every curation run would refuse that store, and the owner would only learn it from a failed run |
| B82 | `STORE.md` gives each integration (a program outside the marketplace that writes into the store) its own state folder `state/integrations/<name>/`, and the curation run never asks for anything under it | an integration's state is its own; reading it would download files the run does not need and let a foreign program steer the curator |
| B83 | A `config.json` that names an add-on m2b no longer has (`herdr`, `backup`, and `band`, which became part of the core) loads as before and that entry is ignored with its settings; `m2b addons on` and `m2b config set addons.<it>...` refuse it with one line saying why it was removed; `m2b addons off` removes the entry and changes nothing else; `m2b curate take-over` does not list it | an update must not break a working machine over a setting nobody reads, and the owner needs a way to tidy it up that says why |
| B123 | Setup records the answer `read_sessions`, true or false, as `curation.read_sessions` in the machine config (B115); without the answer the recorded value stays, so a machine that was never asked reads no session; an answer that is neither true nor false is refused before a file is written | reading what someone typed needs their yes, and running setup again to repair a machine must neither withdraw that answer nor assume it |
| B136 | A current item under a topic (`### <name> (<word>, <word>)` in the current section) stays out of the session start and comes in with its topic, at the start of a session whose project path names the topic and before a prompt that names it (B44, B49), below the topic's facts under `#### Current`; a current item above the first topic reaches every session. Headings with one name, in either section, are one topic, named by a word of any of them, and a topic may stand under current alone | what the owner is working on for one customer must not reach a session about another, and a topic that comes in brings all of itself |
| B142 | `m2b search` answers the hits of a file together, in line order, and the files in the order of the answer, whatever order they were read in: `memory/` first, there `MEMORY.md` before the other files by path; then `corpus/`, then `inbox/`, in both the newest note first by the time in its name, never by the time of the file; a month's journal comes after the notes of its month and before older notes; a file whose name carries no time comes after every dated one of `corpus/` or of `inbox/`, by path. The lists of files not searched keep their order | the `/m2b-search` pane and the model's tool (B104) show the first 100 hits, and those should be what curation wrote and what is newest, not the oldest notes; in a synced folder the time of a file is when it arrived on this machine |
| B143 | The session-start hook, the prompt hook, `m2b search` and the mod's tools hand a model text from the store without the characters that draw nothing: what Unicode calls default ignorable (soft hyphen, fillers, direction marks and bidirectional controls, zero-width space, word joiner, invisible operators, variation selectors, byte order mark, tag characters), without the zero-width joiner and non-joiner, which emoji and several scripts need. The session-start hook takes them out of the distillate, the prompt hook out of a topic's facts (B49) and the mod out of what its tools answer (B104); `m2b search` takes them out of a hit's text, as text and as JSON, and writes them out as `<U+XXXX>`, the two joiners too, in a path, in the command that fetches a file and in why a file could not be read, because a name without its hidden character is another file's name. The core and the mod keep the same table, and every character that undoes a step (B56) is in it | a model does not draw, so it loses nothing, and a character nobody sees can carry text or bytes; with a list each, the core let through what the mod removed: variation selectors, the soft hyphen, fillers |
| B146 | `m2b doctor` starts the plugin's `bin/m2b-prompt-hook` with `--check`, within the seconds `hooks/hooks.json` gives the hook, and reports `prompt-hook: answers` with the hook's line. Asked so, the hook reads what a prompt makes it read (machine config, store, distillate), notes no topic as shown, prints one line and exits 1 with the reason it would otherwise swallow; a store without a distillate is no failure. `does not answer` (with that reason, or when the hook is slower than allowed) and `missing` (the plugin's hooks do not name the command, or it cannot be started) count as problems | the hook prints nothing on any error (B49), so one that never works looked the same as a prompt that named no topic |
| B148 | Of a failed run the session start says when and on which machine it failed and in which steps, by the names of the steps the record lists as failed (a name that is not a step's name is left out), and never why: the reason stays in the run record, where `m2b status` and the review show it. Of a run that left no record it names the run log, and of a run record that cannot be read it says which field is wrong without quoting its value | a reason can repeat what a model said when its run broke, the end of what an add-on's command printed, or a file's name, and a notice stands in m2b's own voice above the line that marks the distillate as data |
| B150 | In a store on the `folder` backend a file is a conflict copy when it has the name Dropbox or Syncthing gives one and the file it names as its original lies next to it. Dropbox: `<stem> (<label>)<ext>`, the label without a bracket in it and holding `conflicted copy` or `in Konflikt stehende Kopie`, in any case. Syncthing: `<stem>.sync-conflict-<8 digits>-<6 digits>`, then nothing or `-` and up to seven of the characters A to Z and 2 to 7, then the extension. The original is `<stem><ext>`; a copy without an extension has an original without one. Such a copy is treated like iCloud's (X8): removable only when it equals its original byte for byte (by `lint fix` in the archive, B21, and of a task file, B157, and by normalize in the inbox), not compared, and so not removed, while it or its original is evicted (B6) or cannot be read, which never stops the look at the other files, and not a task of its own in `tasks/`, where lint names it (B157). In every backend only a file is an original, never a folder and never a symlink, which could point at the copy. Each backend knows the names of its own service only: the folder backend not iCloud's `<stem> <n>.<ext>`, the iCloud backend not these two | which service syncs a folder is not known, and a setting for it could be wrong and would then recognize nothing; before, a conflict in such a store became a second task, a second capture or a note reported for its name |
| B151 | At a session start the distillate hook, before it prints anything and also where the distillate is off, notes the URL of every git remote of the repository the session's folder lies in, with the address a remote is pushed to when that is another one, in machine state (`session-remotes/`, one file per folder, never in the store), in every session, with the top of the repository the folder lies in (the nearest folder above it that holds `.git`, found without git). A URL is noted without the user and password before its host, as the repository's configuration writes it and as git rewrites it (`url.<base>.insteadOf`), and a repository another user owns is read like one's own.
